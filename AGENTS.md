# AGENTS.md — правила работы с DMXWB

Этот файл обязателен для чтения любой моделью/ассистентом **до любого изменения проекта**.

## 1. Источники истины

Читать в следующем порядке:

1. `AGENTS.md` — процесс совместной разработки и обязательный формат handoff пользователю.
2. `docs/PROJECT_STATE.md` — текущий подтверждённый SHA, завершённые этапы и текущий gate.
3. `docs/TECHNICAL_SPEC.md` — утверждённое техническое задание конечного приложения.
4. `docs/ROADMAP.md` — последовательность реализации, границы gates и критерии PASS.

Не восстанавливать старую архитектуру по истории Git, прошлым исследованиям или предположениям, если она не отражена в этих документах.

## 2. Текущая продуктовая архитектура

DMXWB — специализированная программная подсистема Wiren Board 8.5.1, реализуемая как один C++20 daemon.

Главная функция проекта — стабильное управление физическим освещением по DMX512 и возможность внешнего управления тем же DMX-выходом по Art-Net.

Основные компоненты:

- физический DMX512 через встроенный RS-485;
- default port `/dev/ttyRS485-1`;
- WB MQTT как логический источник Fixture/Group/Scene;
- Art-Net как прямой внешний источник DMX-каналов;
- явный selector `WB MQTT / ART-NET`;
- статический web в `www`, взаимодействующий с backend исключительно через MQTT;
- systemd;
- persistent config/state;
- полностью офлайн-устанавливаемый production bundle для Wiren Board.

Эксплуатация предполагается в доверенной локальной LAN. Authentication/authorization, Mosquitto ACL и отдельная security-модель `/mqtt` не входят в scope DMXWB.

Полные требования находятся в `docs/TECHNICAL_SPEC.md`.
Порядок реализации находится в `docs/ROADMAP.md`.

## 3. Роли

### Пользователь

Пользователь владеет локальным репозиторием и GitHub.

Пользователь:

- скачивает подготовленный ZIP;
- распаковывает его поверх локального проекта;
- выполняет выданные команды сборки/запуска/тестов, если они нужны текущему шагу;
- сообщает ассистенту фактический результат проверки или ошибку;
- после PASS выполняет выданный Git-блок;
- отправляет ассистенту новый полный SHA из `git rev-parse HEAD`.

### Ассистент

Ассистент **не пишет и не push-ит напрямую в репозиторий пользователя**.

Ассистент:

- работает только от последнего явно подтверждённого полного SHA;
- перед изменением скачивает с GitHub все необходимые исходные файлы именно с этого SHA;
- пишет/изменяет код и документацию локально в своей рабочей среде;
- готовит финальные файлы, а не diff/patch;
- упаковывает изменённые/новые файлы в root-relative ZIP;
- выдаёт пользователю законченный handoff текущего шага в формате раздела 5;
- при ошибке остаётся в текущем gate и исправляет только причину FAIL;
- при получении нового полного SHA считает предыдущий шаг завершённым и использует этот SHA как единственную базу следующего шага.

## 4. Git base protocol

Текущий подтверждённый SHA всегда хранится в `docs/PROJECT_STATE.md` и дополнительно приходит от пользователя в сообщении после commit.

**Последний SHA, явно присланный пользователем, имеет приоритет как база следующего изменения.**

После каждого commit пользователь выполняет:

```powershell
git rev-parse HEAD
```

и присылает полный SHA ассистенту.

Полученный полный SHA становится единственной базой следующего изменения.

Нельзя строить следующий пакет от:

- приблизительного состояния;
- branch name;
- локально предполагаемого `HEAD`;
- SHA, который не был подтверждён пользователем после предыдущего шага.

Если SHA в `PROJECT_STATE.md` устарел относительно нового SHA, присланного пользователем, текущий документационный пакет должен обновить `PROJECT_STATE.md`.

## 5. Обязательный формат взаимодействия на каждом шаге

Каждый законченный шаг ассистента передаётся пользователю **в следующем порядке**.

### 5.1. Краткое описание шага

Сначала 1–3 предложениями написать:

- что делаем сейчас;
- что является границей текущего шага/gate;
- что сознательно не входит в этот шаг, если это важно.

### 5.2. Получение исходных файлов и выполнение работы

До подготовки результата ассистент:

1. берёт последний полный SHA пользователя;
2. скачивает с GitHub необходимые для шага файлы именно с этого SHA;
3. изучает `AGENTS.md`, `PROJECT_STATE.md`, соответствующие части `TECHNICAL_SPEC.md` и `ROADMAP.md`;
4. при необходимости использует актуальную официальную документацию в интернете;
5. вносит код/документацию;
6. выполняет доступные локальные проверки результата.

Пользователю не требуется вручную собирать patch из текста ответа.

### 5.3. ZIP с готовыми файлами

Если шаг изменяет файлы проекта, ассистент обязан создать ZIP:

- внутри только финальные изменённые/новые файлы текущего шага;
- пути относительно корня репозитория;
- без внешнего каталога `DMXWB/`;
- после распаковки файлы сразу ложатся в правильные места проекта;
- не использовать patch/diff как основной способ передачи изменений.

Ассистент даёт ссылку на ZIP.

### 5.4. Команда распаковки

Сразу после ссылки на ZIP дать готовую команду PowerShell для распаковки поверх локального проекта.

Текущие стандартные пользовательские пути:

```text
Downloads: C:\Users\pereverworkki\Downloads
Project:   C:\Projects\DMXWB
```

Формат:

```powershell
Expand-Archive -Path "C:\Users\pereverworkki\Downloads\<PACKAGE>.zip" -DestinationPath "C:\Projects\DMXWB" -Force
```

Если пользователь позже явно укажет другие пути, использовать новые пути.

### 5.5. Сборка / запуск / тесты

Если текущему шагу нужны команды сборки, запуска, deployment или тестов — выдать их после распаковки и сгруппировать **в один логический блок** (или в явно разделённые блоки Windows/WB, если используются разные машины).

Если такие команды для шага не нужны — **не выдавать пустой или формальный блок**.

Не смешивать Windows и Wiren Board команды без явных заголовков.

Для терминала Visual Studio не использовать PowerShell backtick continuation.

### 5.6. Что проверить

Если результат можно/нужно проверить пользователю, кратко и конкретно перечислить:

- что должно произойти;
- какой результат означает PASS;
- какие ошибки/вывод нужно прислать ассистенту при FAIL.

Если отдельной пользовательской проверки нет, не придумывать её искусственно.

### 5.7. Git-команды

В том же handoff дать один отдельный Git-блок. Пользователь выполняет его **после успешной проверки шага**.

Стандартный формат:

```powershell
Set-Location C:\Projects\DMXWB

git add .
git status --short
git commit -m "<meaningful commit message>"
git push

git rev-parse HEAD
```

Правила:

- не использовать `git diff` как обязательный шаг для пользователя;
- commit message должен описывать именно текущий gate;
- последняя Git-команда всегда `git rev-parse HEAD`;
- после выполнения пользователь присылает либо ошибку, либо новый полный SHA.

Если пользователь прислал ошибку — следующий ответ продолжает **тот же gate**, без перехода дальше.

Если пользователь прислал новый полный SHA — предыдущий шаг считается PASS/committed, и можно переходить к следующему шагу `ROADMAP.md`.

## 6. Формат пакетов изменений

Когда изменяются файлы проекта:

- пакет содержит **финальные файлы**, а не patch/diff;
- пути в ZIP идут относительно корня репозитория;
- нельзя добавлять внешний каталог `DMXWB/`;
- код и относящаяся к нему документация обновляются вместе;
- после распаковки пользователь должен получить готовое рабочее дерево текущего шага.

## 7. Документация во время разработки

Документация ведётся постоянно.

### `docs/TECHNICAL_SPEC.md`

Конечные требования. Менять только при реально согласованном изменении требований/архитектуры.

### `docs/ROADMAP.md`

Порядок реализации и критерии этапов. Это инструкция будущим моделям о том, **что делать следующим после получения нового PASS SHA**.

Обновлять, если меняется последовательность, scope или критерий PASS будущих gates.

### `docs/PROJECT_STATE.md`

Краткая оперативная точка продолжения:

- текущий подтверждённый SHA;
- завершённые этапы;
- текущий gate;
- что подтверждено тестами;
- что осталось сделать;
- известные проблемы;
- следующий конкретный шаг.

Обновлять вместе с каждым завершённым этапом/пакетом, если изменилось фактическое состояние проекта.

### `README.md`

Короткая актуальная точка входа. Не превращать в журнал разработки.

### `AGENTS.md`

Менять только при изменении процесса совместной работы, обязательных инженерных правил или структуры handoff.

Не создавать параллельные документы с дублирующими архитектурными решениями без необходимости.

## 8. Состояния инженерных утверждений

Использовать:

- **Confirmed** — доказано исходниками, тестом или измерением.
- **Decided** — принято как требование/архитектурное решение.
- **Hypothesis** — рабочее предположение, ещё не доказано.
- **Deferred** — сознательно отложено.

Не выдавать Hypothesis за Confirmed.

## 9. Gate discipline

Каждый этап должен иметь узкую проверяемую цель согласно `docs/ROADMAP.md`.

Если тест шага не прошёл:

- не переходить к следующему шагу;
- диагностировать причину в рамках текущего gate;
- минимизировать scope исправления;
- подготовить исправленный пакет того же gate;
- повторить проверку.

PASS основан на фактическом результате теста/оборудования, если gate требует такой проверки.

Получение нового полного SHA от пользователя после выполнения Git-блока означает, что пользователь завершил текущий шаг и разрешает переход к следующему gate.

## 10. Приоритеты реализации

1. стабильный физический DMX output;
2. корректность source switching;
3. надёжность Art-Net и автоматическое восстановление;
4. корректная Fixture/Group/Scene модель;
5. MQTT-интеграция;
6. static web;
7. полностью офлайн deployment и диагностика.

Web, MQTT callback, persistence и Art-Net parser не должны блокировать DMX output loop.

## 11. Hardware safety

При физических измерениях RS-485/DMX не давать инструкций по подключению earth-grounded oscilloscope ground к A/B без подтверждения модели прибора и безопасной схемы измерения.

## 12. Что не использовать как текущую архитектуру

Старые исследования MOD1/WBEC/custom kernel были исследовательской веткой и удалены из рабочего дерева.

Не предлагать возвращаться к:

- DMX engine внутри WBEC STM32;
- custom `wbec-uart` как текущему плану;
- MOD1 как текущему DMX output;

если пользователь явно не изменит утверждённое ТЗ.

Текущий путь — встроенный RS-485 + C++ userspace согласно `docs/TECHNICAL_SPEC.md`.
