# AGENTS.md — правила работы с DMXWB

Этот файл обязателен для чтения любой моделью/ассистентом **до любого изменения проекта**.

## 1. Источник истины

**Источник истины проекта — актуальное состояние репозитория DMXWB.**

Перед каждым шагом ассистент обязан получить из GitHub текущее состояние репозитория и скачать все файлы, необходимые именно для этого шага.

Документы внутри репозитория читать в следующем порядке:

1. `AGENTS.md` — процесс совместной разработки и формат передачи результата пользователю.
2. `docs/PROJECT_STATE.md` — текущее состояние, завершённые этапы, текущий gate и ближайшая работа.
3. `docs/TECHNICAL_SPEC.md` — согласованные требования к конечному приложению.
4. `docs/ROADMAP.md` — последовательность реализации, границы gates и критерии PASS.

Git history может использоваться для диагностики и понимания происхождения изменения, но не заменяет актуальные файлы репозитория как источник текущей архитектуры.

Не восстанавливать старую архитектуру по прошлым исследованиям или предположениям, если она не отражена в актуальном репозитории.

## 2. Продуктовая модель

DMXWB — специализированное расширение возможностей контроллеров **серии Wiren Board 8 (WB8)**, реализуемое как C++20 daemon.

DMXWB не заменяет Wiren Board и не является самостоятельной SCADA или отдельной универсальной системой автоматизации.

Приложение использует штатную инфраструктуру Wiren Board там, где это предусмотрено архитектурой проекта:

- встроенный RS-485 для физического DMX512;
- локальный MQTT/Mosquitto;
- интеграцию с экосистемой Wiren Board;
- systemd;
- штатный web/nginx-контур для статического интерфейса;
- локальную сеть для Art-Net.

Основные функции DMXWB:

- стабильный физический DMX512 output;
- WB MQTT как логический источник Fixture/Group/Scene;
- Art-Net как прямой внешний источник DMX-каналов;
- явный selector `WB MQTT / ART-NET`;
- persistent config/state;
- статический web, взаимодействующий с backend через MQTT;
- полностью офлайн-устанавливаемый production bundle.

Эксплуатация предполагается в доверенной локальной LAN. Собственная authentication/authorization/ACL-модель DMXWB не входит в scope приложения.

Полные продуктовые требования находятся в `docs/TECHNICAL_SPEC.md`.
Порядок реализации находится в `docs/ROADMAP.md`.

## 3. Среда разработки

Основная пользовательская среда:

```text
Windows
Visual Studio 2026
Project: C:\Projects\DMXWB
```

На ноутбуке пользователя также установлена локальная Linux-среда.

Разделение задач:

### Windows / Visual Studio 2026

Используется для:

- основной работы с локальным проектом;
- CMake/MSVC host build;
- host unit tests;
- проверки Windows/non-Linux частей проекта.

### Локальный Linux на ноутбуке

Используется для:

- Linux-specific build/tests;
- POSIX/Linux compile checks;
- подготовки целевой сборки для WB8, включая cross-build, если он требуется архитектурой целевого контроллера;
- подготовки production artifacts.

### Контроллер WB8

Контроллер является прежде всего:

- runtime target;
- hardware integration target;
- местом проверки RS-485/DMX;
- местом проверки MQTT/Art-Net/systemd/web;
- местом финального acceptance.

Обычная production-сборка приложения не должна требовать компиляции исходников непосредственно на контроллере WB8.

### Docker

**Docker в проекте не используется.**

Не предлагать Docker как build, runtime, deployment или test dependency, если пользователь явно не изменит это решение.

## 4. Роли

### Пользователь

Пользователь владеет локальным репозиторием и GitHub и самостоятельно вносит изменения в репозиторий.

Пользователь:

- скачивает подготовленный ассистентом ZIP;
- распаковывает его поверх локального проекта;
- выполняет команды сборки/запуска/тестов, если они нужны текущему шагу;
- проверяет результат;
- при FAIL присылает ошибку/вывод;
- при PASS выполняет Git-команды;
- самостоятельно делает commit и push;
- присылает новый полный SHA из `git rev-parse HEAD`.

Новый SHA после успешного шага означает, что изменение внесено пользователем в репозиторий и можно переходить к следующему шагу, если он предусмотрен.

### Ассистент

Ассистент **не пишет, не commit-ит и не push-ит напрямую в репозиторий пользователя**.

Ассистент:

- перед каждым шагом читает актуальный репозиторий;
- скачивает с GitHub все необходимые для шага исходные файлы;
- пишет/изменяет код и документацию локально в своей рабочей среде;
- выполняет доступные локальные проверки;
- готовит финальные файлы, а не patch/diff;
- упаковывает изменённые/новые файлы текущего шага в root-relative ZIP;
- передаёт пользователю законченный handoff;
- при FAIL остаётся в текущем шаге/gate и исправляет причину ошибки;
- после нового SHA пользователя заново сверяется с актуальным репозиторием перед следующим шагом.

## 5. Принцип шагов

Работа делится на небольшие законченные шаги.

Границы и правила конкретного шага могут меняться в зависимости от задачи. Не нужно искусственно добавлять сборку, hardware test или другие действия, если они не нужны для проверки данного изменения.

Стандартный шаг состоит из следующих частей.

### 5.1. Краткое описание шага

Сначала 1–3 предложениями указать:

- что делаем;
- границу текущего шага;
- что сознательно не входит в него, если это важно.

### 5.2. Получение исходных файлов и выполнение работы

До подготовки результата ассистент:

1. проверяет актуальное состояние репозитория;
2. скачивает с GitHub необходимые для шага файлы;
3. читает относящиеся к задаче документы и код;
4. при необходимости сверяется с актуальной официальной документацией;
5. вносит изменения;
6. выполняет доступные локальные проверки.

Пользователю не требуется вручную собирать patch из текста ответа.

### 5.3. ZIP с готовыми файлами

Если шаг изменяет файлы проекта, ассистент создаёт ZIP:

- внутри находятся **финальные файлы**, а не patch/diff;
- включаются только изменённые/новые файлы текущего шага;
- пути идут относительно корня репозитория;
- внешний каталог `DMXWB/` внутри ZIP не добавляется;
- после распаковки файлы сразу попадают в правильные места проекта.

### 5.4. Команда распаковки

После ссылки на ZIP ассистент даёт готовую PowerShell-команду.

Стандартные пользовательские пути:

```text
Downloads: C:\Users\pereverworkki\Downloads
Project:   C:\Projects\DMXWB
```

Формат:

```powershell
Expand-Archive -Path "C:\Users\pereverworkki\Downloads\<PACKAGE>.zip" -DestinationPath "C:\Projects\DMXWB" -Force
```

Если пользователь позже явно укажет другие пути, использовать новые.

### 5.5. Сборка / запуск / тесты

Если для шага нужны команды сборки, запуска, deployment или тестов, ассистент выдаёт их после команды распаковки и группирует в один логический блок.

Если используются разные среды, допускаются явно разделённые части одного блока, например:

```text
Windows / Visual Studio 2026
Local Linux
WB8
```

Если команды не нужны, этот раздел не выводится.

Не смешивать команды разных сред без явного обозначения.

Для терминала Visual Studio не использовать PowerShell backtick continuation.

### 5.6. Что проверить

Если пользовательская проверка нужна, кратко указать:

- что должно произойти;
- какой результат означает PASS;
- какой вывод/ошибку прислать при FAIL.

Если отдельной проверки нет, не придумывать её искусственно.

### 5.7. Git-команды

После успешной проверки ассистент выдаёт отдельный Git-блок.

Стандартный формат:

```powershell
Set-Location C:\Projects\DMXWB

git add .
git status --short
git commit -m "<meaningful commit message>"
git push

git rev-parse HEAD
```

Правила:

- commit message должен описывать текущий шаг;
- последняя Git-команда — `git rev-parse HEAD`;
- пользователь самостоятельно выполняет commit/push;
- после выполнения пользователь присылает либо ошибку, либо новый полный SHA.

Если пользователь прислал ошибку, следующий ответ продолжает тот же шаг/gate.

Если пользователь прислал новый SHA, текущий шаг считается внесённым в репозиторий и разрешён переход к следующему шагу, если он есть.

## 6. Git и рабочая база

SHA используется для трассируемости, но не заменяет репозиторий как источник истины.

Перед началом шага ассистент должен знать фактическое состояние репозитория, от которого готовится пакет.

После пользовательского commit:

```powershell
git rev-parse HEAD
```

пользователь присылает новый SHA.

Этот SHA:

- подтверждает завершение предыдущего шага;
- позволяет однозначно связать PASS с commit;
- является ориентиром для проверки следующего состояния репозитория.

Перед следующим изменением ассистент всё равно повторно читает актуальный репозиторий.

Если актуальное состояние GitHub неожиданно отличается от присланного SHA, ассистент сначала определяет причину расхождения и не строит изменения на предполагаемом состоянии.

## 7. Формат пакетов изменений

Когда изменяются файлы проекта:

- пакет содержит финальные файлы;
- patch/diff не используется как основной способ передачи;
- пути в ZIP идут относительно корня репозитория;
- нельзя добавлять внешний каталог `DMXWB/`;
- код и относящаяся к нему документация обновляются вместе, когда изменение затрагивает требования или фактическое состояние;
- после распаковки пользователь получает готовое рабочее дерево текущего шага.

## 8. Документация во время разработки

Документация ведётся постоянно и должна соответствовать актуальному репозиторию.

### `docs/TECHNICAL_SPEC.md`

Конечные требования. Менять при согласованном изменении требований или архитектуры.

### `docs/ROADMAP.md`

Порядок реализации, scope gates и критерии PASS.

Обновлять, если меняется последовательность, scope или критерии будущих gates.

### `docs/PROJECT_STATE.md`

Краткая оперативная точка продолжения:

- актуальное состояние репозитория/рабочая база;
- последний подтверждённый PASS;
- текущий gate;
- что уже реализовано;
- что подтверждено тестами;
- что осталось проверить;
- известные проблемы;
- следующий конкретный шаг.

### `README.md`

Короткая актуальная точка входа. Не превращать в журнал разработки.

### `AGENTS.md`

Процесс совместной работы, среда разработки, обязательные инженерные правила и формат handoff.

Не создавать параллельные документы с дублирующими архитектурными решениями без необходимости.

## 9. Состояния инженерных утверждений

Использовать:

- **Confirmed** — доказано исходниками, тестом или измерением.
- **Decided** — принято как требование/архитектурное решение.
- **Hypothesis** — рабочее предположение, ещё не доказано.
- **Deferred** — сознательно отложено.

Не выдавать Hypothesis за Confirmed.

## 10. Gate discipline

Каждый engineering gate должен иметь узкую проверяемую цель согласно `docs/ROADMAP.md`.

Если тест gate не прошёл:

- не переходить к следующему gate;
- диагностировать причину в рамках текущего gate;
- минимизировать scope исправления;
- подготовить исправленный пакет;
- повторить проверку.

PASS основан на фактическом результате теста/оборудования, если gate требует такой проверки.

Документационные или организационные шаги могут существовать внутри текущего engineering gate и сами по себе не означают PASS этого gate.

## 11. Приоритеты реализации

1. стабильный физический DMX output;
2. корректность source switching;
3. надёжность Art-Net и автоматическое восстановление;
4. корректная Fixture/Group/Scene модель;
5. MQTT-интеграция с Wiren Board;
6. static web;
7. полностью офлайн deployment и диагностика.

Web, MQTT callback, persistence и Art-Net parser не должны блокировать DMX output loop.

## 12. Hardware safety

При физических измерениях RS-485/DMX не давать инструкций по подключению earth-grounded oscilloscope ground к A/B без подтверждения модели прибора и безопасной схемы измерения.

## 13. Что не использовать как текущую архитектуру

Старые исследования MOD1/WBEC/custom kernel были исследовательской веткой и не являются текущей архитектурой.

Не предлагать возвращаться к:

- DMX engine внутри WBEC STM32;
- custom `wbec-uart` как текущему плану;
- MOD1 как текущему DMX output;
- Docker как build/runtime/deployment слою;

если пользователь явно не изменит согласованные требования.

Текущий путь — C++ userspace-приложение как расширение контроллеров серии WB8, физический DMX через встроенный RS-485 и интеграция со штатной инфраструктурой Wiren Board.
